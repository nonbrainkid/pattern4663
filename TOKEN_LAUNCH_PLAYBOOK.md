- CoinGecko `/search` returned no exact listed coin for `PTRN`, `PATTERN`, or `P4663` at check time. CoinGecko search only covers assets indexed by CoinGecko, so absence is not global uniqueness.

**Mandatory disambiguation rule:** always present `PATTERN / $P4663` with the canonical domain and `Robinhood Chain • 4663`; after deployment, add the checksum-form verified contract address. The token name or ticker alone is never an identity proof.

## 4. Publishing guardrails

### Pre-launch versus post-launch gate

- **Pre-launch-safe:** Posts 01–13 only. Posts 05, 07, 10, 11, and 13 still require the canonical domain placeholder to be replaced with a controlled HTTPS domain.
- **Post-launch-only:** Posts 14–20. Do not schedule them with unresolved placeholders. Their gate opens only after deployment is final, chain ID is confirmed as `4663`, the explorer page resolves, source verification status is checked, and the same checksum CA appears on the canonical site and in both launch drafts.
- The teaser and countdown never imply that a token is already tradable. If deployment slips, stop the queue and publish a plain timing update—never fake continuity.
- Never use the Robinhood logo, Robinhood green, “official,” or layout that implies ownership, partnership, sponsorship, approval, or endorsement.

### Contract and domain double-check procedure

1. **Control the domain:** verify registrar access, HTTPS, correct redirect behavior, and an immutable launch page location. Remove every staging domain and placeholder.
2. **Create the source record:** copy the deployed checksum CA directly from the deployment receipt; record chain ID `4663`, transaction hash, deployer, exact name `PATTERN`, exact symbol `P4663`, explorer address URL, token URL, and source-verification status in an internal launch manifest.
3. **Verify on the official explorer:** confirm the address is a contract on Robinhood Chain, the token metadata matches, the deployment transaction is final, and published source/bytecode verification shows the intended artifact. “Contract found” is not the same as “source verified.”
4. **Three-surface comparison:** two people independently compare the full checksum CA, character by character, across the deployment receipt, Blockscout, canonical domain, Post 14, Post 15, Post 16, and Post 20. The generic `pattern_announcement_1080x1350_v01.png` contains no CA and is not part of this comparison. Never compare shortened addresses.
5. **Fresh-session test:** open the canonical site and explorer from a clean browser session and a second network/device. Confirm that redirects do not change the domain and that copy buttons return the exact CA.
6. **Publish in sequence:** Post 14 first, then the text-only Post 15. Link Post 15 beneath Post 14. Recheck both live posts. Only then continue to Post 16.
7. **Correction rule:** if any identifier is wrong, stop all queued posts. Do not silently edit or delete the only record. Publish a clear correction from the canonical account and update the site; if contract integrity is uncertain, state that interaction is paused.
